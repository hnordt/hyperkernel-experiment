# Todo comparison

This experiment asks a concrete question: how does the current Hyperkernel
handle Todo writes and reads compared with a traditional CRUD implementation?

Both applications expose the same Todo contract, use Deno's built-in
`node:sqlite`, and run on one long-lived SQLite connection with one writer. Both
databases are file-backed and refuse to start unless SQLite confirms WAL mode.
No dependency was added.

## Run it

From the repository root:

```sh
deno task todo:test
deno task todo:serve
```

Then open <http://127.0.0.1:8000>. The server keeps independent databases in
`experiments/todo-comparison/data/`, so switching engines never mixes their
state.

The browser app uses a native custom element, `fetch`, `AbortController`, and
DOM APIs. Hyperkernel mode adds an event log and a position slider. Historical
snapshots are read-only; returning to live state enables mutations again. The
log opens on the latest 1,000 records and provides older/newer page controls for
longer histories.

## Implementations

| Lane           | Todo write                                                      | Audit log | Purpose                                                             |
| -------------- | --------------------------------------------------------------- | --------- | ------------------------------------------------------------------- |
| `crud`         | Prepared SQL against `todos`                                    | No        | Traditional baseline                                                |
| `audited-crud` | Prepared event insert and Todo projection in one transaction    | Yes       | Isolates the inherent cost of retained history from kernel overhead |
| `hyperkernel`  | Current `dispatch()` appends an event and applies its projector | Yes       | Architecture under test                                             |

The browser exposes the two application implementations, `crud` and
`hyperkernel`. `audited-crud` exists only in the benchmark as a diagnostic
control.

Every lane uses the same `STRICT` Todo table and these connection settings:

```sql
PRAGMA journal_mode = WAL;
PRAGMA synchronous = NORMAL;
PRAGMA busy_timeout = 5000;
```

Every logical create and erase gets its own `BEGIN IMMEDIATE` transaction. The
CRUD baseline deliberately does not batch writes because the current kernel
commits each dispatch separately.

## Hyperkernel model

The application defines three recorded facts:

- `TodoCreated`, containing the complete initial Todo snapshot
- `TodoCompletionChanged`, containing the Todo ID and accepted completion state
- `TodoDeleted`, containing the Todo ID

One projector applies those events to `todos`; typed kernel queries implement
point reads and ordered list reads. Missing and no-op mutations are checked
before dispatch so the log does not claim a fact that did not occur. That
pre-read is safe here only because the experiment explicitly owns the sole
writer connection.

The current kernel has no public event-log or replay API. The experiment keeps
that coupling in `event_log.ts`: it reads `__hyperkernel_events` directly,
parses each JSON record with the matching Zod schema, and folds events into an
in-memory `Map`. Time travel reconstructs a read-only snapshot; it never rewinds
the live projection or dispatches old events again.

## HTTP surface

| Method   | Path                                      | Result                                   |
| -------- | ----------------------------------------- | ---------------------------------------- |
| `GET`    | `/api/:engine/todos`                      | Live ordered Todo list                   |
| `POST`   | `/api/:engine/todos`                      | Create from `{ "title": string }`        |
| `PATCH`  | `/api/:engine/todos/:id`                  | Change `{ "completed": boolean }`        |
| `DELETE` | `/api/:engine/todos/:id`                  | Idempotent removal                       |
| `GET`    | `/api/hyperkernel/events?after=A&limit=L` | Validated event page and latest position |
| `GET`    | `/api/hyperkernel/todos?at=N`             | State after event position `N`           |

IDs and timestamps are generated by the HTTP boundary before either store is
called. Static files come from an exact allowlist and are served with a
same-origin Content Security Policy.

## Benchmark

Run the default lifecycle workload:

```sh
deno task todo:bench
```

Or choose the workload and retain raw samples:

```sh
deno task todo:bench --todos=10000 --warmup=2 --samples=9 --list-reads=5 \
  --json=experiments/todo-comparison/todo-benchmark.json
```

The task deliberately limits JSON output to a path inside
`experiments/todo-comparison`, matching its scoped Deno write permission.

For each lane and sample, the harness creates a fresh file database and times:

1. sequential creation of all pre-generated Todos;
2. one deterministic, shuffled point read per Todo;
3. repeated full-list reads;
4. sequential erasure of every Todo;
5. the combined measured lifecycle.

Input generation, migrations, store construction, file inspection, integrity
checks, result validation, reporting, and cleanup are outside the timed regions.
Runtime validation, event serialization, statement behavior, authorizer work,
and transaction commits remain inside because they are real request-path costs.

Each lifecycle runs in a dedicated Web Worker isolate. This keeps native runtime
resources from an earlier closed database from contaminating the next supposedly
fresh sample; worker startup remains outside every reported phase. Warmup
lifecycles are isolated too: they warm shared module and filesystem caches
without carrying a previous database's runtime resources into a measured worker.
They do not pre-JIT the measured worker.

This is therefore a **cold-isolate lifecycle** benchmark, not a steady-state
throughput test of one already-JIT-warmed worker. The JSON report includes all
raw samples, median, p95, and maximum duration plus the operation rate at the
median duration. With fewer than 20 samples, the terminal table labels and shows
the maximum rather than presenting the maximum as a useful p95 estimate.

The report also includes Hyperkernel/CRUD ratios, Hyperkernel/audited-CRUD
ratios, event counts, WAL confirmation, integrity checks, and storage figures.
Active-file figures break out the median main database, WAL, and shared-memory
files while the connection is open; the displayed total is their sum. These are
WAL allocation snapshots, not retained database size. The non-freelist page
figure is an estimate from SQLite page statistics. A list-read operation is one
complete list query, not one returned row.

Do not treat one run or one ratio as a universal pass/fail threshold. Compare
absolute latency with the application's needs, then use the audited control to
separate the price of event history from avoidable framework overhead.

See [the recorded local baseline](./BENCHMARK_RESULTS.md) for 1,000- and
10,000-Todo results.

## Expected trade-offs

Hyperkernel and CRUD read the same projection table, so their database read work
is structurally similar. Hyperkernel additionally installs its SQL authorizer
and validates typed query output.

Writes are intentionally asymmetric: traditional CRUD mutates one row, while
Hyperkernel retains an event and mutates the projection atomically. After
creating and deleting `N` Todos, the CRUD table is empty and Hyperkernel keeps
`2N` events. Audited CRUD makes that feature cost visible without pretending it
is framework overhead.

Historical replay is currently `O(events)` and depends on the kernel's private
event-table shape. Snapshots/checkpoints, schema versions, event metadata,
public replay APIs, and multi-writer coordination are outside this experiment.
Those become the next design boundary if histories or concurrency grow enough to
make full replay or the single-writer precondition unacceptable.
